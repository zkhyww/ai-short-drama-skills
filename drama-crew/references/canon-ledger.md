# 长篇状态管控（正典账本机制 · 融合版）

> 使用场景：**集数 ≥ 10，或需要逐集批量续写完整剧本正文时**先 Read 本文件。只出「集纲+首集+分镜」的预览规模时，账本随四件套顺带产出、存档备用即可，不额外展开。
> 不写长篇正文时无需读取本文件。

**设计原则：管控动作嵌进交付物，不新增流程环节。** 团队跑法（角色、弹窗、节奏）与预览规模完全不变。
**责任人定版（v6.12.1 收口）**：**文茵**（编剧）产出本批「账本增量+自检声明」→ **质检批由青梧**（正典官）合并增量、跑冲突核查、输出正式账本；**非质检批由主理人机械粘贴合并**，不读正文提炼、不做冲突核查 → 主理人除此之外只调度与验收，不改写账本内容。

## 1. 账本 Schema（核心六栏 + 题材可选第七栏 · v6.8.2 定版，编剧初始化、随批更新）

`正典账本.md` 与成稿 md 同目录。**文件头部必须有进度头，一眼可验账本是否最新：**

```
当前进度：正文已写至第 {X} 集｜账本最后更新：第 {X} 集
```

**核心六栏**（所有题材必填）：

| 栏 | 记什么 |
|---|---|
| 人物状态 | 每个主要人物当前身份/处境/位置 |
| 知情范围 | 谁知道哪些秘密（防知情穿帮的核心栏） |
| 关系变化 | 每次关系转折的触发事件与当前关系 |
| 关键道具 | 持有人/状态/去向（转手、损坏、公开、消耗必记） |
| 伏笔 | 埋设集 → 预定回收集，超期标红 |
| 集末状态 | 最新一集结束时明线/情感线/暗线各一句快照 |
| **成长体系**（**可选第七栏**：玄幻/古装/科幻/升级类题材必填，现实题材省略） | **主角及关键角色的成长跨集追踪**：`境界/等级：E01 炼气三层 → E05 筑基`；**四线并行**——个人战力/势力资源/声望地位/装备道具（吸收自早期 n8n「宇宙企划书」升级系统思路，见 world-bible.md 第 2 节） |

> 现实题材成长体系栏可省略（成长=身份/处境变化，已在人物状态栏覆盖）；升级类题材缺失本栏=违规。

**知情判断证据链（仍写入「知情范围」栏，不新增栏）**：每次认定角色或观众已经知道某事实，先按三步写清：`可见/可听载体 → 直接支持的最强结论 → 尚未证明的推断`。角色看到血迹，只能直接支持「这里发生过流血」，不能自动升级成「某人已经死亡」；角色听见半句通话，也只能取得半句实际支持的信息。推断可以成为人物行动依据，但必须标为推断，不得当作已证实正典，也不得让后续角色凭空共享。

## 2. 回写：文茵出增量 → 青梧合并（主理人只调度）

- 文茵每批交付物固定**多附一段「账本增量」**（只列本批变更行）+ 一份自检声明（六栏逐栏已更新✅）。**质检批次**由青梧粘贴合并进账本并跑八项冲突核查；**非质检批次**由主理人直接粘贴合并（不读正文提炼、不做冲突核查）。
- **增量落位口径（唯一 · v6.14.0 收口）**：账本增量**随批落盘为独立文件** `{项目名}_增量_E{起}-E{止}.md`（与「正文真源分批落盘」对称，质检批交接与跨会话恢复直接读文件，不翻正文批次尾部找增量段）；增量文件随批次递增归档，合并完成后在文件头部标一行「已合并至账本（第X集）」，避免误当未处理增量。**禁止只在正文文件尾部内嵌增量段**——正文真源与账本增量是两类交付物，混写会让下游（交接单引用、青梧质检、跨会话恢复）多一次解析成本（实测五项目两种口径并存导致交接引用不可比）。
- **冲突处置顺序（v6.15.1 收口）**：先确定权威事实——用户最新确认的正文或明确修订指令优先，账本只是记录层，不得反向覆盖已锁定正文；再定位**首次偏离权威事实的可编辑位置**。账本记录错误就修账本；未锁定正文写错时由青梧标注、交文茵返修；用户已确认正文不得自动修改，只能报告冲突。两份同级已确认材料互相矛盾、无法判断哪份更新时，无明确权威时才上报用户裁决。处理后沿后续批次顺链核对受影响行，避免只修晚期症状。
- **显式时间锚核查**：正文出现具体钟点、日期、倒计时或“第 N 天”等锚点时，账本在人物状态或集末状态中保留当前时间进度。跨集重复同一句时间动作不因文字相同自动判错，但必须与账本推进一致；账本已经跨时段而正文仍批量停在旧钟点，定位首次冻结处交文茵修正文与后续受影响行，禁止只在末集改一个数字。
- 一个项目一份活动账本，旧版标「归档」。
- **世界观档案联动**：玄幻/古装/科幻类项目，账本与 `world-bible.md`（世界观档案）并行维护——账本记剧情连续性，世界观档案记世界真实性；文茵每批同时附「世界观增量」（新地点/新规则/境界突破），随账本同流程合并（质检批次青梧并、非质检批次主理人并）。

## 3. 下发前强制 3 件事（查账本不需要引导，规则强制）

任何续写/修改/分镜任务下发前，编排者固定执行（不允许凭记忆带状态）：
1. **Read `正典账本.md`**，核对进度头与目标集一致，粘贴最新账本原文（核心六栏+适用第七栏）进下发模板；
2. **Read 成稿 md 的上一集结尾场次**（制作侧景川承接时则读锚定表+已用 S 序号），粘贴承接段；
3. 确认硬设定原文在模板中未缺项。三件齐了才发任务；账本进度头落后于正文时先补回写再发。

## 4. 跨会话恢复（换窗口/重开会话不丢状态）

新会话承接旧项目时，开工第一动作：
1. Read 项目目录下 `正典账本.md`（取进度头+核心六栏+适用第七栏）与成稿 md 末尾集；
2. 在回复里向用户回显「当前进度：第 X 集｜下一批：第 X+1 起」，再按第 3 节强制 3 件事续跑。
——账本的「可查」由「先读文件再干活」的强制规则保证，不依赖会话记忆。

## 5. 批量续写（批次粒度 · v6.14.0 收口）

**批次粒度（唯一口径）**：**正文 10-20 集/批为基准，按体量自适应**——总集数 ≤24 时可全程单批或 12 集/批；30-40 集 2-3 批；60 集及以上每 20 集一批（与分批质检节奏对齐：质检批 = 正文批边界重合，青梧一次进场同时并账本+核冲突，不额外拆批）。用户明确指定批大小时从用户，但**不建议低于 5 集/批**——批过小会成倍增加增量文件、质检进场与合并次数（实测 5 集/批 × 12 批 vs 20 集/批 × 3 批，前者交付成本显著更高而质量无增益）。

**下发模板（固定复用）：**

```
你是短剧创作团的编剧文茵。继续创作《{剧名}》第 {起}—{止} 集正文。
【硬设定】{题材/风格/受众/集数/载体/平台/选题方案要点}
【正典账本（当前状态，账本原文）】{核心六栏+适用第七栏}
【上一集结尾场次原文】{承接用}
【集纲（本批对应集的行）】{集纲对应行}
【你的任务】交付：1) 本批各集正文（标准剧本格式，每集结尾落在集纲标注的卡点上）
2) 账本增量（核心六栏中本批变更行，升级类题材含第七栏；随批单独落盘 {项目名}_增量_E{起}-E{止}.md）
3) 自检声明：逐集确认无知情穿帮、无道具去向矛盾、伏笔是否按期回收，发现问题先自行返修再交付。
```

主理人合并增量、扫自检声明，即可进下一批——没有独立的检查环节、没有审批仪式，用户只在「继续/暂停」层面参与。

## 6. 明确不采用的机制（防流程膨胀）

不建多目录项目体系、不做三层编辑链与双代理、不跑程序硬闸、不设评分表。这些是 60 集级连续交付的基建，30 集内团队接力+账本增量已覆盖同等风险。
