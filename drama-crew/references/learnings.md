# 创作经验库（跨项目自进化 · 顾临维护，改稿后按需加载）

> **解决的问题**：skill 本身是静态的，用户的改稿反馈以及用户要求借鉴的外部成功/失败案例，过去只能靠手动改规则才能沉淀。本文件建立**「反馈或案例 → 提取有边界的方法候选 → 验证 → 升格」**的闭环，让团队越用越贴合用户偏好，同时不把案例声量或作者说法冒充已验证规则。
> **借鉴来源**：drama-script-writing 的 S6 自我学习模块（改稿后自动对比初稿 vs 修改版）。去掉其「每步等确认」重交互部分，只留经验沉淀机制。

## 1. 触发时机（写死）

**用户对任何成员的产出做过修改/纠正，或明确要求吸收外部成功/失败案例后，顾临必须主动执行本流程**——不等用户重复提醒、不依赖终审是否通过；普通问答不触发，不把随口讨论自动沉淀。

**持久化纪律（v6.8.7 定版）**：普通改稿只在**当前任务内部**提炼经验候选，不落盘、不额外追问；只有用户明确说「记住 / 写入经验库 / 以后这样」或对提炼条目明确认可时，才写入本文件持久化；**写入后不自动删除、不自动压缩清退**（超体量时向用户提示并等裁决）。

| 用户行为 | 处理 |
|---|---|
| 用户手动改了产出，或说「这里改成XX」 | 改稿完成后在任务内提炼经验候选（不落盘不追问） |
| 用户说「写入」/「记下来」/「记住」 | 经验条目写入本文件，持久保留 |
| 用户说「**以后就这样**」/「**以后不要XXX**」/「**改规则**」 | **快速升格通道**：直接改写 references 正式规则 |
| 用户要求借鉴或收入外部成功/失败案例 | 先用既有资料/样本建立有来源、有条件的方法候选；收入案例资料区时不只存 URL，保存可取得原文、关键回复与关联参考媒体，逐项记录未取得范围及采集/观看/复现状态；不复制进全域规则 |
| 用户没表态 | 候选只在任务内有效，随任务结束丢弃；不落盘、不暂存、不倒计时 |
| 文茵写批前六行自检触发补缺（联网搜词库/资料） | 补缺产物随账本增量交主理人，顾临审后按升格对照表沉淀进对应 references——运行时补缺是经验库的主动来源（v6.17.5） |

## 2. 提取流程

```
1. Read 本文件摘要（避免重复记录）
2. 先定位主责原段与薄弱点；反馈型只索取/比对用户改过部分的最终版，案例型优先消费用户已给的资料/样本
3. 案例型把可取得原文、关键回复、关联参考媒体与复现记录留在项目或用户案例资料区，未取得范围如实记录；采集成功、完整观看与生成复现分别标状态，不能互相代替。全域库只保留必要来源定位、条件、机制与验证结论
4. 区分「已见事实 / 作者声称 / 我方推断」，记录模型输入与后期条件、资料缺项、适用 / 不适用范围；资料截断属于采集缺项，不能据此改写作者提示词或推断精简能优化效果
5. 候选写成「在何种条件下解决什么问题、依靠什么机制、怎样核验」，不从案例抽取动作、镜数、尺度等数量配额；无复现不宣称可复现
6. 用户已授权（说「记住/写入/记下来」或明确认可条目）→ **直接写入本文件，不再二次确认**；用户未授权 → 条目只在任务内有效，随任务结束丢弃
7. 超体量不打断创作，只在用户主动维护经验库时提示并等裁决
```

## 3. 经验条目格式

```
[YYYY-MM-DD] [维度]
- 来源与授权：来源 URL / 作者或发布者 / 版本日期 / 授权状态；案例资料区同时定位已取得原文、关键回复、关联参考媒体、未取得范围及采集/观看/复现状态；用户反馈型写对应项目与反馈定位
- 观察：区分 已见事实 / 作者声称 / 我方推断；不把热度、点赞或转发写成效果证明
- 规律：在何种条件下解决什么问题、依靠什么机制、怎样核验
- 适用范围：题材、节点、载体、目标模型，以及输入与后期条件、资料缺项和适用 / 不适用范围
- 例外：哪些条件下不适用，现有硬边界是否仍须保留
- 行动：可选机制、实际验证与迁移去向；未验证时写待验证，不直接下发生产
- 置信度：高 / 中 / 低；按证据具体性、适用边界与复现状态判断
```

## 4. 写入规则（8 条）

1. **不把一次经验普遍化**：具体案例的可取得原文、关键回复、关联参考媒体与各证据状态留在项目或用户案例资料区，不只存 URL；候选须写条件、问题、机制、核验、适用范围、例外与证据，不足时维持低置信
2. **只记会改变后续判断或产出的经验**：包括 AI 常犯错误、用户偏好和用户授权吸收的外部案例机制，不记显而易见的常识
3. **与现有规则重复的不记**（写前先 Read 对应 references 核对）
4. **与核心规则冲突的**标记「需讨论」，不直接写入正式规则或下发
5. **写入以用户授权为前提**——用户明确说「记住/写入/记下来」或明确认可条目时直接写入不再二次确认；用户未授权的候选不落盘
6. **不因纠正一个过度硬约束就禁止所有硬约束**——事实锁、知情边界、世界规则、授权、合规与格式契约等必要硬边界按各自主责文件保留
7. **升格看具体证据与适用边界**——不依点赞量或重发次数计高置信；采集、完整观看与生成复现是不同证据，按风险用相称的文字、接口或生成验证；允许只适用于特定模型和后期条件的打斗、巨物、玄幻方法，不强求普适。无复现不宣称可复现，但不强制付费试制，也不阻塞项目其他已获授权工序
8. **写入、复盘、升格共用同一授权边界**——只认可方法价值不等于允许发布原始案例；低置信或待讨论条目不得自动作为生产或终审规则下发，保留用户已授权条目，不自动删除

## 5. 项目复盘仪式（项目交付后顾临必跑 · v6.17.6 增）

项目交付（或用户宣布项目告一段落）后，顾临执行收尾，把项目内沉淀的经验候选固化进仓库——**skill 的进化以项目为节拍**：

```
1. 汇总本项目已获用户授权的经验条目：已持久化条目 + 补缺产物（词库/语料/资料）+ 终审红灯新模式 + 外部案例方法候选
2. 逐条按来源、条件、证据、验证状态和授权判定去向：升格进 references（按第 6 节对照表）/ 留 learnings / 丢弃；低置信或待讨论不自动注入生产或终审
3. 跑合同测试确认全绿 → 升 patch 版本（SKILL.md version + CHANGELOG + README + 测试钉子）
4. 提交推送，commit message 列明本项目升格了什么——git 历史即 skill 成长史
```

**作者分流（v6.17.9 用户裁定定版：按账号身份分流，不按机器）**：
- **仓库所有者（zkhyww，本机本账号）**：**直推 main**——推送前本地跑绿合同测试，CI push 触发自动复验，红了立即修复重推；项目复盘产物同样直推，一个项目 = 一个版本 = 一个进化 commit。
- **其他设备/其他账号（协作者）**：一律 **PR**——条目必须带证据（哪个项目/用户什么反馈/置信度），CI（`.github/workflows/contract-tests.yml`）机器先拦，人只审「这条经验值不值得进规则库」；默认 squash 合并，保持 git 历史一项目一节点。
- **CI 红处置**：main 直推 CI 红立即修复重推；PR 红不合入，先修再审。

## 7. 体量维护

- **触发**：本文件超过 5KB 或条目超过 30 条
- **动作**：**先向用户提示并等裁决**，不自动删除任何条目；用户同意后高置信度经验可「毕业」升格进 references 正式规则（升格不等于删除原条目，是否清理由用户定）；压缩后在变更记录留痕（日期/处理了几条/保留哪些/原因）
