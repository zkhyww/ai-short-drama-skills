# 团队协作

## 版本真源

GitHub `main` 是团队共享基线。个人 WorkBuddy 目录是运行副本，不应成为长期分叉的唯一版本。

修改时先在仓库分支完成编辑、验证和评审，再把通过的版本复制到个人 Skill 目录。不要同时在仓库和运行目录各改一份，然后靠记忆合并。

## 分支与提交

- 一个问题使用一个短分支，例如 `fix/unreviewed-qc` 或 `feat/model-card-xxx`。
- 修改范围要小；主责文件已有位置时，直接替换旧规则，不在文件末尾追加补丁段。
- 同一逻辑单元形成一个提交，Skill 修改和对应文档、验证证据放在一起。
- 不提交剧本项目、媒体文件、模型返回、Cookie、Token、`.env` 或个人工作区路径。

## 版本号

- 只修正文案但不改变执行合同：通常不必升级版本，由维护者裁定。
- 修复冲突、改变路由或调整执行判据：升级 patch。
- 新增兼容能力、模型卡或可见工作流：升级 minor。
- 破坏既有交接结构或要求团队迁移：升级 major。

版本号修改后，同时更新 README 和 CHANGELOG。两个 Skill 不要求总是一起升级。

## 最小验证

如果本机安装了 WorkBuddy 的 `skill-creator`：

```powershell
python -B "$env:USERPROFILE\.workbuddy\skills\skill-creator\scripts\quick_validate.py" '.\drama-crew'
python -B "$env:USERPROFILE\.workbuddy\skills\skill-creator\scripts\quick_validate.py" '.\drama-studio'
```

每次提交还要检查：

1. Markdown 围栏成对；
2. 本地与跨包引用没有断开；
3. 修改过的合同在主流程、角色卡和下发模板中口径一致；
4. 不含凭据、本机绝对路径、`.skill` 测试包或缓存；
5. 至少有一个能复现旧问题的行为场景。

模型卡修改要额外验证“指定模型是否真的加载对应卡”“静态卡与实时接口冲突时谁优先”。声音流程修改要覆盖首次发声、向后筛选、冻结回填和失效重选。

## 评审顺序

1. 先看执行是否会断路、误放行或制造不存在的输入；
2. 再看跨文件口径是否一致；
3. 最后才处理措辞和排版。

评审结论要落到文件与证据。已经没有 P1 时，应转入行为测试，不继续做没有真实失败证据的全包重写。

## 发布步骤

1. 合并通过评审的分支；
2. 运行两个 validator 和敏感扫描；
3. 实际打包到临时目录，核对包内文件数；
4. 删除测试包；
5. 确认工作树干净，再推送 `main`；
6. 团队成员按 CHANGELOG 决定是否升级运行副本。

发现线上问题时优先用新提交修正。已经共享的历史不要强制改写，也不要用破坏性命令清理团队成员的未提交工作。
