# 特点与架构

## 双 Skill 分工

`drama-crew` 和 `drama-studio` 以定稿剧本交接为边界：

```text
题材与目标
  → drama-crew：选题、人物、结构、正文、账本、合规、终审
  → 标准/直通交接
  → drama-studio：资产、分镜、提示词、声音、剪辑、制作 QC
```

创作侧定义故事事实、因果、欲望、阻力、选择和代价。制作侧把这些内容翻译成可见、可听、可剪的镜头，不擅自改变故事事实。

## 按需加载

主文件只保存流程骨架。题材规范、写作方法、模型能力和制作维度放在 `references/`，由主理人根据任务命中后原文注入。

这种做法解决两个常见问题：一是所有规则同时进入上下文后互相打架；二是模型把没有命中的经验数字当成机械门槛。没有恋爱线的项目不会加载恋爱专项，未指定视频模型时也不会遍历全部模型卡。

## 交接合同

交接不只是“把文件给下游”。`review_state` 明确区分：

- `reviewed`：终审、合规和账本可以作为下游已验证输入；
- `unreviewed`：不补造报告，制作侧从严检查并声明能力边界；
- `not_provided`：用户直接提供的裸本，不把缺失证据写成“无风险”。

制作主理人再把交接材料中的命中片段分别贴给丹青、景川、闻笙、陆离和严恪，而不是把整包内容复制给每个角色。

## 条件化创作规则

`romance_axis=on|off` 在选题锁定后确定。关闭时，互通心意、表白位置、纯约会集等判据统一为 N/A，不扣分、不触发返修。亲情、友情、师徒、团队关系和人物内在弧线仍然可以承担 B 线。

其他创作数字多数是诊断信号，不是逐集配额。执行者先看观众体验和故事因果，再判断是否需要调整。

## 模型能力合同

景川的能力限制按三层裁决：

```text
execution 实时 provider/adapter/version schema
  > 用户指定的目标模型能力卡
  > 未指定模型的通用保守默认
```

不同生成模式分别核对时长、参考图、首尾帧、画幅、Prompt 上限和声音能力。换模型时只重判不兼容的镜头及真实依赖，不让一个局部差异导致全批作废。

Gemini Omni 1.1 Flash 卡针对 `flow2api-secure-account-pool` 的公开适配能力编写，不把 Google Flow 网页上存在但 adapter 没有开放的功能写进执行合同。

## 声音连续性

文字声音指纹描述角色“怎样说话”，母音色描述角色“实际用哪个声音”。两者不能混用。

闻笙从每个角色首次发声起试听候选，片段要能听清音色、节奏、重音、停连、气息和句尾落点。冻结母音色后，之前的临时对白要回生成；普通改句仍只重录这一句。

逐句声音表演包含意图、潜台词、承重词、思维节拍、速度、强度、音高、气息停顿和句尾落点。接口不支持的控制项不会被伪装成已执行。

## 安全边界

- Skill 不附带模型凭据或付费调用权限。
- `planning_only` 不伪造图片、视频、音频或试听结果。
- 开源和模型内置母音色不增加许可证字段；真人克隆音色不在当前流程内。
- 审批编号由发行或报审上游提供，制作侧不自行生成。
- 经验库只有得到用户明确授权时才持久写入。
